# Purchase verification service

Requires Node 24 or newer. Run `npm ci` in this directory, set `DATABASE_PATH` to a persistent volume path, provide Google Application Default Credentials securely, and run `npm start`. The service account needs the minimum Play Console permissions to read and acknowledge purchases for `com.lilopia.game`. Never commit credentials or include them in the Android app.

Terminate TLS at a trusted reverse proxy. Expose only POST /verify; set a request-body limit of 8 KiB, request timeout, and per-client rate limiting there. This service ignores forwarded IP headers deliberately and applies a bounded per-socket-address limiter. Behind a proxy this is a shared limit, so size it appropriately in infrastructure before live testing. Disable body logging and redact tokens from provider/proxy access logs. Use one service instance with its durable SQLite volume; do not put the database on ephemeral storage.

The service fixes the package name and product allowlist; queries Google every time; rejects pending, canceled, consumed and multi-quantity purchases; stores only the SHA-256 token hash, product and check time; and acknowledges before returning an entitlement. A failed acknowledgement returns no entitlement and is retried on Restore. No entitlement is inferred from the hash database. A purchase token is bearer proof: transport and logging protections are required. This implementation has no player accounts or cross-account token binding.

POST JSON: `{"productId":"com.lilopia.expansion.beach_vacation","purchaseToken":"<Google Play token>"}`. Success returns the matching product ID and `verified:true`. Errors never echo tokens or Google error URLs. Automated tests use mock Google responses and test the actual HTTP server without credentials; they are not live purchase validation.

Before enabling purchases: exercise the real Play API with license testers, acknowledgement failure/retry, pending approval, cancellation, refund/revocation and reinstall/restore. Current app rechecks ownership on resume/start and requires connectivity for paid packs after reopening. Continuous offline entitlements, real-time developer notifications and a durable acknowledgement queue are not implemented. Monitor successful fulfillment and implement those services before promising stronger offline/instant-revocation behavior. Decide and disclose actual log/database retention and deletion handling in the privacy policy before deploying this service for players.
